## 2. 产品定位与导航

将 Wiki 作为目录旁边的可追溯知识层：用户能够找到一个概念或项目，知道上游哪些页面引用了它，并回到准确版本的原文。站内收录和引用关系均不表示本站推荐、测试或认可相关内容。

顶部保持四项：**资源库 / 知识 / 更新 / 收藏**。第二项扩展现有“专题”入口，避免在移动端增加第五个等宽导航项。

| 已实现路由 | 用途 |
| --- | --- |
| `/[locale]/wiki` | 知识索引入口，搜索与浏览综述、概念、实体 |
| `/[locale]/wiki/[id]` | Wiki 元信息、来源及引用关系页 |
| `/[locale]/topics` | 保留现有精选专题列表和原 URL |
| `/[locale]/topics/[slug]` | 保留现有专题导读和原 URL |

Wiki 和专题页面均归属“知识”导航。知识入口用轻量文字链接进入“精选专题”；上游 Wiki 与本站专题使用不同的来源说明，不将两者混成一个“精选”列表。现有首页专题快捷入口和资源卡的 Name / Desc / URL / Tags 单列结构保持不变。

知识索引默认显示全部文档，可用现有选择控件按综述、概念、实体筛选。类型名称和数量来自实际导入结果。没有内容的类型不制造空入口；未来增加类型须同时验证实际文档和对应数据规范。

## 3. 初版文章页：元信息与原文跳转

文章页采用当前 VS Code 主题的单列主体与辅助信息区，主要内容为：

- 原始标题、文档类型、主题和已知的原文语言；未识别语言只在详情标注。
- 当前不存储或展示简介、别名，不自动补写摘要。
- “阅读上游原文”入口、实际文件路径及固定来源版本。
- 本站首次收录、最近索引变化、最近成功同步时间，分别标注。
- 已解析的 Wiki 引用、反向引用和目录资源引用。
- 无法解析的引用及其原始标识，给出简短状态说明。

页面明确说明“本站展示索引与引用信息，正文请前往上游阅读”。不能在没有正文时使用“阅读全文”“全文搜索”或阅读时长等暗示已完整呈现正文的文案。

原文链接优先指向已验证的固定提交文件，保证用户看到的内容与本站元信息一致。可另提供上游当前版本入口，但必须清楚区分“本次收录版本”和“上游当前版本”。不将整个 `index.md` 或综述全文加载进浏览器作为索引页内容。

## 4. 引用关系与资源双向关联

引用关系必须来自明确的原文证据，不能由标题相似、同属分类或搜索相关性推导。

| 展示名称 | 关系依据 | 必须保存的证据 |
| --- | --- | --- |
| 本文引用的 Wiki 页面 | 上游正文或结构化字段中的显式 Wiki 引用 | 来源文档、原始目标、可定位的来源位置、解析目标 |
| 引用本文的页面 | 上述 Wiki 引用关系的反向查询 | 同一条关系记录，不维护另一份手工反向表 |
| 本文引用的目录资源 | 显式外部 URL，或已验证来源投影中能唯一确定的资源 URL | 原始 URL、来源位置、目录资源 ID、两侧来源版本 |
| 引用此资源的 Wiki 页面 | 上述目录资源引用的反向查询 | 同一条关系记录 |

Wiki 内链解析遵循实际语法，区分目标、显示别名与章节锚点。只在实际文档表中解析目标；存在多个候选时标为歧义，不选择看起来最像的一项。反向引用自动从成功解析的关系生成。

资源匹配复用目录现有 canonical URL 规则，保持已有资源 ID 和收藏有效。匹配时可以使用规范化 URL，展示和跳转仍保留原文 URL 及有意义的锚点。不能仅凭同一个域名、仓库所有者或项目名称把引用关联到资源。

页面使用“引用”“来源”等中性标签，不能把引用次数写成质量分数，也不能因为被 Wiki 引用而增加“精选”标记。源文档若只是列出某个工具，本站只呈现这个引用事实，不生成使用步骤或组合建议。

## 5. 真实来源投影映射

Wiki 中的来源名称可能是生成流程使用的逻辑投影，不一定是仓库中的实际文件。`sources` 目录没有文章这一事实尤其不能被忽略。每个可点击来源都必须通过同一固定提交的真实文件清单验证。

建议为每次解析保留：原始来源标识、映射规则、实际文件路径、条目定位信息、验证提交、解析状态和失败原因。映射结果是证据链，不是另行生成的内容。

| 来源形态 | 允许链接的条件 | 无法满足时的展示 |
| --- | --- | --- |
| README 投影 | 上游数据能确定对应 README，且该固定版本确实存在该文件；章节链接还需验证章节 | 保留原始来源名称，显示“来源路径未解析” |
| skills 投影 | 能由上游路径或明确映射确定实际 skill 文件，且在该版本存在 | 不按名称猜测 `SKILL.md` 路径，不创建空链接 |
| 描述投影 | 能确定实际描述文件及对应条目；文件在该版本存在，条目确实可定位 | 显示原始标识及缺失或歧义状态 |
| Wiki 文档引用 | 目标属于已验证文档清单；指定锚点时还需验证章节 | 区分“目标文档未找到”和“章节未找到” |

约束如下：

- 不把 `wiki/sources/...` 一类逻辑地址直接拼成 GitHub 链接。
- 不用仓库首页或任意 README 静默替代缺失来源，造成已经找到证据的假象。
- 实际文件可定位、具体章节不可定位时，可以分别给出文件链接与“章节未解析”说明，不能伪造章节锚点。
- JSON 等描述文件若没有稳定的网页条目锚点，只链接经过验证的文件，并展示实际条目键；不能伪造 GitHub 行号。
- 当前联合同步将 README 与 Wiki 固定到同一提交；不得保留另一个提交的 Wiki 后声称仍为同源快照。
- 上游 `confidence` 只可显示为“上游自报置信度”，保留原始值和出处。不得转换成本站评分、“已验证”状态或推荐等级。

无法解析不是隐藏引用的理由。保留原始标识可让用户理解上游写了什么，也便于之后修正映射；只有成功验证的目标才变成可点击链接。

## 6. 搜索与发现

首页搜索接通三个明确分组：资源、Wiki、专题。每组显示自己的命中数量，Wiki 先展示少量结果及“查看全部”，避免大规模实体结果挤掉资源目录。现有资源分类、平台、引擎等筛选只作用于资源，不能造成 Wiki 结果似乎也经过相同筛选的误解。

Wiki 专用搜索覆盖标题、类型与主题，并包含十语言界面的类型名称及少量通用主题同义词。原始名称始终可搜索；界面语言切换保留查询。当前没有别名、简介或正文索引，不展示正文片段或虚构命中位置。

有查询时优先精确标题，其后为真实元信息匹配；没有查询时默认依次展示综述、概念和项目条目，也可选择名称或索引变化时间排序。搜索相关性与引用关系保持独立。不能因为两个结果经常同时出现就自动创建关系，也不生成攻防学习路线或操作链。

## 7. 十语言界面与原文语言

导航、内容类型、状态、空态、来源说明和引用标签提供现有全部十种界面语言：`en`、`zh-CN`、`zh-TW`、`ja`、`ko`、`de`、`fr`、`es`、`it`、`ru`。

文档标题保持原始内容，正文留在上游。中文界面并不意味着正文已翻译：原文语言已确认且与界面语言不同时，标注需前往来源语言原文阅读；语言没有可靠证据时，在详情显示“语言未识别”，不猜测。

当前不存储 Wiki 简介或正文翻译。未来若接入上游生成的简介或翻译，应另行记录语言与来源，不能呈现为本站编辑导读。切换界面语言不会改变被引用的原文版本。

## 8. 固定版本与增量同步

同步在数据任务中完成，浏览页面不触发上游抓取。大文档只在导入阶段处理；客户端获得搜索和展示所需的元信息，不获得所有 Wiki 正文。以下记录当前实现，未来多文件方案单独说明。

### 8.1 单提交与完整文件清单

任务开始时只解析一次上游完整提交 SHA，并将该值传给 README 目录导入、描述导入、Wiki 导入和来源映射。`sync:data --commit` 可接收指定提交，各子流程使用同一值。保留不同提交 Wiki 的跳过导入操作会失败，避免混合源版本。

采用 Git Trees API 时，先读取该提交的根树，定位 `wiki` 子树 SHA，再枚举该子树；README 和实际需要的 skills、描述来源只读取相应树或路径，不递归获取整个仓库的归档目录。

每次树响应都检查 `truncated`。Wiki 子树的递归响应若被截断，放弃该响应作为完整清单的依据，改为非递归逐级枚举子树，并继续检查每次响应；如果仍不能获得完整清单则本次同步失败。非递归请求必须省略 `recursive` 参数，传 `false` 仍会启用递归。这些行为以 [GitHub Git Trees 官方文档](https://docs.github.com/en/rest/git/trees#get-a-tree) 为依据。

文件存在性、文档数量和索引覆盖校验都基于完整树清单；不能把截断结果中的缺失误报成上游删除。每个选定路径记录所属树、blob SHA 和字节大小，随后只按该固定对象读取内容。

### 8.2 Blob 缓存与可配置容量边界

Wiki 原始内容缓存按 blob SHA 存储；缓存文件与下载内容均核对普通文件类型、字节大小和 Git blob SHA。相同 blob 可跨提交复用，只有缺失或校验失败的 blob 需要获取。当前通过固定提交的 Git partial clone 和 sparse checkout 下载选定正文，不逐篇调用 Git Blobs API；每次导入重新解析缓存文本，不缓存解析结果。

文件选择阶段先根据完整树记录执行容量检查，随后对读取内容的实际大小和 SHA 校验，缓存命中不能绕过限制。默认缓存位于 `node_modules/.cache/ags-wiki-blobs`，可通过 `WIKI_CACHE_DIR` 指定目录；工作流恢复和保存该缓存，缓存不进入快照和自动提交白名单。来源投影读取 README、描述、skills 对应的真实文件清单；未读取的来源文本不被声称已核实其章节。

当前默认容量边界为：

| 限制 | 初始值 | 依据与处理 |
| --- | --- | --- |
| 单个 Wiki Markdown 文件（含索引） | 1 MiB，即 1,048,576 bytes | 通过 `WIKI_MAX_DOCUMENT_BYTES` 配置；文件选择和读取校验均执行边界 |
| 一次 Wiki 导入的总文本 | 32 MiB，即 33,554,432 bytes | 选定 Wiki 正文与 `index.md` 的总字节，包括缓存命中内容；通过 `WIKI_MAX_TEXT_BYTES` 配置 |

这两项是可配置的工程边界，本次真实导入已在默认限制内完成，不代表未来所有版本都适用。未来文档增长或读取范围变化需重新校准；超限时本次同步失败并保留旧快照，不截断文本、不跳过超限文档、不自动放宽限制。目录 README 和既有描述导入继续执行各自的容量检查。

### 8.3 已采用：Catalog.wiki 单文件原子快照

实际同步过程为：

1. 获取固定版本的完整文件清单，区分文档文件、辅助文件和不存在的投影。
2. 校验索引覆盖、文档唯一性、结构化字段及来源存在性。
3. 生成元信息快照、显式引用关系、反向索引和无法解析记录。
4. 根据文档路径身份及 blob SHA 比较已有快照，记录新增、变化和删除。
5. 将资源目录和 Wiki 一起验证，写入 `catalog.json` 的临时文件，再通过同一文件系统内的原子重命名替换正式文件。失败时保留旧快照。

`Catalog.wiki` 保存文档元信息、引用、变化记录、来源提交、索引版本和同步时间，不保存正文。读取端仍读取一个 `src/data/catalog.json`，因此本次没有引入 manifest 或多文件代次目录；客户端仅接收专门投影的轻量字段，不能直接导入完整快照。

历史设计中的 manifest 方案保留为未来拆分多文件时的条件方案：先写不可变代次文件，校验后原子切换 manifest；读取端只能读取它指定的同一代次。不能逐个覆盖多个固定文件名后声称整体原子，也不能只增加 manifest 而不迁移读取端。本次无需该方案。

### 8.4 接入现有 Workflow

`.github/workflows/sync-catalog.yml` 已增加 Wiki blob 缓存恢复与保存，`sync:data` 同时导入资源和 Wiki。因为所有发布数据仍在同一个 `catalog.json`，意外变更检查、变更检测和 `git add` 的提交白名单继续只允许该文件，无需扩展。未来拆分时才需同步更新这三处，只允许经过验证的生成文件，不能扩大成无约束的 `src/data/**`。

现有工作流在固定提交导入后执行链接与仓库 metadata 检查、typecheck、lint、测试、构建及生产 HTTP 冒烟，再提交完整 `catalog.json`。保留串行维护锁与 fast-forward push 行为。Blob 缓存不参与自动提交，任何验证失败都不会进入提交步骤。

### 8.5 变化语义

文档 ID 由稳定的仓库路径生成，同一路径的内容更新保留 ID。当前不推断重命名，路径变化按删除与新增记录，不用相似标题合并。移除记录保留原有固定提交来源；收藏中当前索引不存在的 ID 可清理，但不凭一个未知本地 ID 断言上游曾删除文档。

首次导入只建立基线，本次 3,923 篇文档对应的初始 Wiki 变化列表为空。“首次收录”“索引变化”“上游声明的更新日期”“同步成功时间”分别标注；不能用仓库 push 时间或 `.state.json` 的处理时间冒充某篇文章的更新时间。

同步复用未变化的 blob 缓存，并重新生成引用解析结果。文档新增、删除或 blob SHA 变化形成观察记录；仅导入器解析规则变化不制造原文变化事件。blob 变化也可能只是格式调整，更新记录不表示软件发布或经过核实的知识更新。

## 9. 视觉与交互约束

沿用 `directory.css` 的 VS Code 深色背景、语法配色、文字链接、轻页签及现有 SelectControl。Wiki 列表使用紧凑行与必要分隔，不增加层叠边框、大面积选中底色或关系图背景。

文章主体首先说明来源和用途；桌面可将引用目录放在右侧，移动端顺序排列。大量引用按组分页或展开，不能把数千条引用一次铺满页面。无法解析的来源用普通状态文字说明，不为每条记录增加额外按钮或系统 tooltip。

按钮保留 hover、disabled 与键盘焦点状态。长标题、URL 和十语言标签可换行；手机导航继续保持四项。页面正文的实际语言与界面 `html lang` 分别标注。

## 11. 验收范围与持续检查

本次已通过的本地测试、构建、HTTP smoke 和浏览器检查见开头“实施结果”。以下保留为持续检查边界，不将它们等同于已经完成所有设备组合、故障点或上游内容质量审核。

数据与来源：

- 按每次同步的实际固定提交核对文档数量及 index-to-file 覆盖；历史基线数量不再作为新版本固定断言。frontmatter 解析、正文引用状态及来源映射结果与内容质量分开报告。
- `sources`、`.gitkeep`、规范和状态文件均不作为文章展示；后续版本按真实清单重新计算数量。
- 所有可点击的固定版本文件来源均通过该提交的文件存在性校验；所有声称可定位的条目和章节均有实际证据。
- 每条原始引用都有解析结果；无法解析和歧义不被静默丢弃，不被生成的猜测链接替代。
- 所有资源关联都有明确 URL 或经过验证的来源投影证据；正向与反向引用数量一致，没有仅靠名称建立的关联。
- `confidence` 始终标注为上游自报，未知信息不显示为已核实，普通索引不显示为本站精选。

交互与语言：

- 十语言界面字段齐全；标题原名可搜索；界面语言和原文语言说明准确。
- 搜索分组数量与各组真实结果一致，资源筛选不会静默作用于 Wiki；初版不出现“全文搜索”或虚构正文片段。
- 知识索引、元信息页、引用分页和原文跳转可用键盘完成；焦点可见，禁用态和空态正确。
- 在 320、560、820、1440px 视口检查布局，并覆盖德语、俄语长标签及中日韩文本；无横向页面溢出、遮挡或第五导航项挤压。
- 缺失文档与非法 locale 延续本站真实 HTTP 404、本地化可见内容和 noindex 行为；已保留的旧快照须明确标记其状态。

性能与更新：

- 首页及 Wiki 列表的客户端数据不包含 Wiki 全文，尤其不包含 723,088 bytes 的大型综述或 2,424,032 bytes 的综述集合。
- 引用和列表分页不改变关系总数；构建过程和页面请求不重复下载上游全文。
- 初次导入不产生已有文档的“新发布”记录；一次内容变化不误报其他未变文章。
- 模拟下载失败、解析失败和覆盖不完整时，已发布的上一份完整快照仍可使用。
- 模拟 Git Trees `truncated: true` 时，完成逐级完整枚举或明确失败，不能发布截断清单。
- 测量全部选定文本的实际大小并校准配置；单文档或总文本超限时失败，缓存命中不能绕过限制。
- 相同 blob 在缓存完整时复用；解析器版本变化能重新生成解析产物，正文不必重复下载。
- 当前原子性检查针对完整 `catalog.json` 的临时写入与重命名；未来拆分多文件时，另行验证 manifest 切换和读取端的一致性。
